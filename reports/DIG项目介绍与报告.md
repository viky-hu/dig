# DIG 上海共享单车数据分析与交互可视化项目报告

## 一 项目定位

共享单车连接着城市生活中的许多短距离移动。我们希望通过订单回答三个逐步深入的问题：人们什么时候骑车，一次骑行通常持续多久，骑行活动又集中在哪里、怎样在区域之间流动。DIG 将这些问题组织成一个可以亲自探索的分析系统，让数据处理、统计发现和视觉表达形成连续的理解过程。

项目使用上海地区一个完整月份的共享单车订单样本。经过清洗，102,210 条有效订单呈现出较清晰的早晚高峰、以短时骑行为主的时长分布，以及集中于核心城区的空间结构。这些发现与城市短途接驳的使用场景相吻合。不过，订单本身没有标注出行目的，因此“通勤接驳”是结合统计特征作出的解释，仍需城市设施等外部信息进一步验证。

DIG 的另一条主线是 GSAP 的系统实践。首页的网格重组建立整体结构，悬停插画预告研究主题，窗口展开延续空间关系，清洗实验室则把处理步骤转化为可暂停、可重播的过程。动效承担着引导注意、解释变化和组织演示节奏的作用，使观众既能看到分析结果，也能理解结果怎样产生。

## 二 数据来源与可信度

项目随附的数据说明将公开样本来源指向 Heywhale 的摩拜共享单车数据集，并将其描述为脱敏研究数据。当前分析实际使用本地文件 `mobike_shanghai_sample_updated.csv`，共 102,361 条记录、9 个字段。来源入口与本地文件应分开理解：公开页面提供来源线索，具体规模、字段和统计结论以本项目实际文件为准。参考入口见文末资料依据。

原始字段包含订单、单车和用户三个标识，出发与到达时间，以及起终点各一组经纬度。这些信息足以支持时间、时长、热点和区域流向分析。当前文件不含完整轨迹，也没有天气、站点或出行目的标签；样本规模不等同于上海全市的全量骑行规模。

可信度首先来自清晰的处理规则。Python 脚本依次完成读取、初探、时间解析、时间特征提取、时长计算、异常过滤和结果保存。初探确认当前样本没有缺失值与重复行，因此这一步只检查，不进行填补或去重。随后，从出发时间提取日期、小时、星期和周末标记，再用起止时间差计算分钟数，最终形成 14 个分析字段。

异常过滤按脚本顺序进行：先保留不少于 1 分钟的记录，再保留不超过 180 分钟的记录，检查起终点坐标是否都处于设定的上海近似经纬度范围，最后复核负时长。实际剔除 148 条超长记录和 3 条坐标越界记录，共 151 条，保留率约 99.85%。坐标规则是矩形范围检查，并非精确的行政区边界判定；保留率也只说明规则筛选的结果，不能据此认定数据完全没有误差。

这条处理链最终输出 `cleaned_mobike.csv`。报告使用的订单数、用户数、单车数、小时统计和主要时长指标均与当前 CSV 交叉核对。由此，后面的每一个问题都有可追溯的数据基础。

## 三 系统架构与技术栈

系统采用“离线计算、前端交互呈现”的结构。Python 负责数据清洗、探索性统计、空间聚类和 OD 分析；分析结果以本地统计常量进入前端，再由 React 管理筛选与选择状态，SVG 绘制图形，GSAP 编排图形和界面的变化。首页保持挂载，内容通过叠层窗口打开，同时提供独立内容路由。当前访问页面不会发起在线挖掘任务，也没有数据库或业务后端接口参与这条展示链路。

```mermaid
flowchart LR
    A[原始订单 CSV] --> B[Python 清洗与特征提取]
    B --> C[时间 时长 空间 OD 离线分析]
    C --> D[前端本地统计常量]
    D --> E[React 状态与 SVG 图形]
    E --> F[GSAP 驱动八模块交互报告]
```

图中的分析结果进入前端这一环，目前主要依靠整理后的常量，尚未形成统一、自动更新的数据发布接口。这使演示可以脱离分析环境运行，也意味着分析结果更新后，需要同步维护前端数据。

| 层次 | 当前主要技术 | 在系统中的作用 |
| --- | --- | --- |
| 页面与状态 | Next.js 16、React 19、TypeScript | 组织首页与独立内容路由，管理窗口和交互状态 |
| 图形与样式 | SVG、CSS、Tailwind CSS 4、Lucide | 自绘图表、地图与插画，建立布局和视觉层级 |
| 动画与交互 | GSAP 3、@gsap/react | 编排时间线、滚动联动、路径变化和可控回放 |
| 离线分析 | Python、pandas、NumPy、scikit-learn、Matplotlib | 清洗、统计、KMeans 聚类与分析图表输出 |
| 工程组织 | pnpm workspace、Turborepo | 管理应用、共享包及构建检查任务 |

当前图表直接由 SVG 和 React 实现，没有使用 ECharts。仓库虽然保留了 Three.js 高速背景等组件和相关依赖，但它们没有接入当前首页与八个内容模块的展示主链，不能据此把系统介绍为三维可视化平台。

## 四 沿系统完成一次探索

### 从首页进入项目总览

演示从首页开始。线条先勾勒结构，标题和彩色面板依次出现；向下滚动时，页面固定在视野中，网格逐渐重排，中央自行车图形被描绘出来。研究问题由此成为八个可选择的入口。进入“项目总览”，可以先交代数据规模：有效订单 102,210 条，涉及 16,883 位用户、78,985 辆单车，平均骑行时长为 16.49 分钟，中位数为 11 分钟。它为后续分析建立共同背景。

### 数据清洗让结果有据可循

接着进入“数据清洗”。七个章节把原本连续运行的脚本拆成可以观察的阶段。点击执行后，左侧场景展示记录展开、时间解析、特征派生、异常分流与字段归档，右侧同步高亮实际 Python 源码，下方记录数和字段数在对应节点更新。观众可以暂停、继续、重播本步或重置全部流程。

例如，一条 7 分钟的真实样本帮助解释时长计算；超长记录和坐标越界记录沿不同路径进入拒绝区域；最终，字段重新排列成输出结构。这里回放的是已完成的本地分析，浏览器并不执行 Python。展示的价值在于把处理依据、动作和统计变化放在一起，让人看懂每一步为什么发生。

### 时间规律回答何时需要车辆

数据可信后，先观察一天中的使用节奏。“时间规律”提供全部、工作日和周末三种视角，并支持悬停查看、点击锁定小时。全样本的小时汇总在 08:00 和 18:00 形成明显高峰，其中 18:00 的 10,118 单为最高值。切换工作日与周末时，柱形和面积图平滑过渡，使差异能够被连续比较。

工作日订单为 76,044 条，占 74.40%；周末为 26,166 条。由于样本包含 23 个工作日、8 个周末日，页面在这两种模式下使用各自的日均小时订单量，避免天数不同干扰比较。由此可以更稳妥地观察工作日尖峰与周末较平缓的活跃节奏，而不能只凭总量差异断言工作日的单日需求更高。

### 骑行时长回答一次使用持续多久

接下来进入“骑行时长”。分钟级柱形、分布轮廓和均值、中位数、四分位区间标记共同解释分布。切换“5—20 分钟”或“30 分钟以上”，相应区间被突出，其他部分弱化；选择具体柱形或统计标记，可以进一步查看信息。

按 5 分钟及以上、20 分钟以下的口径，共有 67,957 单，占 66.49%。分布在 7 分钟附近达到峰值，中位数 11 分钟，而均值被右侧长尾拉高至 16.49 分钟。因此，大部分骑行时间较短，少量较长骑行仍然存在。时长支持短途使用的解释，但不能直接换算为骑行距离，更不能据此识别每个人的目的地。

### 空间热点回答需求集中在哪里

时间和时长之后，视角转向城市空间。“空间热点”将六簇统计置于上海行政区轮廓之上。底图路径的数据来源指向 DataV 的上海行政区边界；点击或聚焦热点及排名项，可以查看对应订单量、占比和中心位置。“全市预览”暂时拉远视野，再返回核心城区，让观众理解局部热点与城市整体的关系。

离线空间分析直接以起点经纬度为特征，采用 KMeans，主分析设置 K=6，并以不同 K 值的惯性曲线辅助观察。前三簇共 60,858 单，约占 59.54%，说明需求具有集中性。页面围绕簇中心生成的散点用于示意密度，并非逐条订单的原始位置；区域名称是帮助阅读的概括，也不等于严格的行政区或商圈归属。KMeans 的预设簇数和经纬度距离处理，都是后续可以继续验证的模型选择。

### 区域流向回答区域之间怎样联系

热点说明“哪里多”，区域流向进一步展示“哪里与哪里联系”。页面以六个区域为节点，用环形表示区域内流动，用有向束线表示跨区联系，并提供全部、跨区、区域内、净流向四种模式，以及 Top 5、10、15 的跨区流向排名。选择节点、连线或排名项，会联动呈现对应信息。

按当前前端展示矩阵，102,210 次骑行中有 86,995 次属于区域内流动，占 85.11%，跨区流动为 15,215 次。这里的“区域内”指起终点落入同一聚类区域，不代表同一行政区。连线是区域级关系的概括，没有描绘实际行驶路线；净流入与净流出也只是这个样本窗口内的汇总差额。它可以提供调度研究的线索，距离实时调度决策仍需要车辆存量、时段和路网等信息。

“成员介绍”解释项目如何协作完成：王海涛负责论文文档与讲解答辩，陈书扬负责选题规划和数据挖掘，胡继天负责演示网页与前端交互，喻圣文、王潘毅参与演示文稿的后期深化与优化。介绍分工后，再回到“结论展望”，将早晚高峰、短时骑行、热点集中和区域内流动串成一条解释链，同时说明样本、变量和模型的边界。这样，演示结束时留下的是有依据的认识，以及可以继续验证的问题。

## 五 GSAP 如何贯穿整个系统

### 用滚动与空间连续性建立整体感

首页使用 ScrollTrigger 固定视口，并用 scrub 将滚动位置绑定到时间线进度。代码通过一个进度值插值计算网格轨道，再同步面板与分隔线的几何位置；自行车线条和介绍文字在同一时间线上配合出现与退场。CustomEase 为线条和标志描绘设置专门节奏。网格重组来自几何插值，不能将其笼统归为 Flip 动画。

点击模块后，系统记录入口面板和中央蓝色区域的屏幕位置，通过 SVG 矩形几何变化展开内容窗口，再依次带出侧栏与正文。窗口通过 SVG 的 foreignObject 嵌入 React 内容，将几何转场与可操作的正文组合在一起。关闭时，窗口收回入口，中央蓝色区域恢复，自行车重新描绘。菜单线与自行车线稿还会在悬停时交替出现。这种呼应让观众始终知道内容从哪里展开、返回哪里。

### 八种悬停插画提前解释模块主题

首页每个入口都有独立的 SVG 场景和可反向播放的时间线。它们共享控制方式，却使用不同的视觉隐喻。

| 模块 | 悬停时的主要表现 |
| --- | --- |
| 项目总览 | 册页展开，内部窗口重新排列 |
| 数据清洗 | 粒子进入筛网，异常分离，确认标记描出 |
| 时间规律 | 太阳沿路径移动并变成月亮，云层与星光交替 |
| 骑行时长 | 自行车双轮合拢为计时器，刻度和指针变化 |
| 空间热点 | 分散点向中心聚拢，热点圆环与定位框出现 |
| 流向分析 | 路径展开，粒子沿线运动，箭头指明方向 |
| 成员介绍 | 人物卡片归位，协作网络逐步连接 |
| 结论展望 | 柱形升起，折线与箭头变形并向上延伸 |

其中，DrawSVG 控制描线范围，MorphSVG 处理日月、刻度、折线等路径变形，MotionPath 控制粒子和图形沿曲线运动。指针移开后，时间线反向回到初始状态；再次进入时继续响应。插画因而成为可探索的主题提示，而非一次播放后便失去作用的装饰。

### 用时间线把过程和数据同步起来

清洗实验室集中体现了 GSAP 的过程表达能力。时间线的阶段标签触发源码高亮，检查点更新记录数和字段数，播放进度同时推动底部进度条。异常分流通过 MotionPath 呈现，最后的字段排序先由 Flip 记录旧布局、改变顺序，再补间到新布局；ScrollToPlugin 则让右侧代码区域跟随当前语句滚动。暂停、继续和重播控制的是这套相互关联的过程。

时间和时长图表使用 GSAP 处理柱形尺寸、透明度及轮廓变化，空间热点按底图、散点、中心与标注分层出现。地图的全市预览通过视图变换串起局部与整体。区域流向的筛选主要由 React 状态驱动即时更新，GSAP 参与窗口与地图视野变化；首页流向插画中的路径粒子，不应被描述成详情页持续运行的真实车流。

### 让华丽表现具备可控的工程基础

项目通过 `useGSAP`、`gsap.context` 和组件引用约束动画作用范围，在退出或重建时清理时间线。窗口具有关闭、打开中、已打开、关闭中四种阶段，并通过锁和版本检查控制交接；内容打开时暂停首页滚动触发器，返回后再恢复。清洗回放也使用代次检查，避免旧回调更新新步骤的状态。

这些细节让动画能够承担交互职责。悬停插画支持键盘焦点，部分主要模块根据减少动态效果的偏好跳到结果状态；小屏首页直接采用最终布局。当前适配仍可继续统一，尤其是首页开场与窗口转场。视觉完成度与工程完善程度应分别评价，具体性能还需要帧率、布局开销和不同设备上的测量。

## 六 项目价值与发展空间

DIG 已经形成从处理依据到分析结论、再到交互表达的完整展示链。它的价值在于让观众逐步建立判断：先理解样本如何被处理，再比较时间和时长特征，最后观察空间与流向关系。GSAP 为这条链提供了可见的节奏，也让讲解者能够停留、回放和选择重点。

下一步应先统一结果发布机制。将清洗摘要、小时统计、聚类中心和 OD 矩阵导出为带有口径说明的结构化数据，使前端自动消费同一批结果，并对总量、分组与版本进行校验，可以减少人工维护常量造成的差异。之后再考虑上传样本、触发分析任务和保存分析版本，逐步建设真正的数据服务能力。

分析层面可以引入天气、轨交站点、道路和城市设施，对通勤接驳解释进行验证；采用适合地理距离的处理方式，对比 DBSCAN 等模型，并检查不同参数下热点是否稳定。展示层可以让时间筛选同时影响热点与 OD，也可以增加统一的演示节奏控制。运营建议则需要进一步结合车辆存量和时段需求验证，不能直接由当前汇总图推导补车数量。

这些发展方向都源于现有系统暴露出的实际需求：数据更新需要一致，模型结论需要验证，模块之间需要更紧密的联系。沿着这条路径，项目能够从一份具有表现力的交互报告，逐步发展为支持持续分析的工具。

## 附录 演示准备与资料依据

### 建议演示顺序

首页滚动并展示日月与计时器悬停效果 → 总览交代规模 → 清洗演示执行、暂停和过滤归档 → 时间切换工作日与周末 → 时长突出核心区间 → 热点选择与全市预览 → 流向切换跨区和区域内、选择排名 → 成员分工 → 结论与后续发展。每次打开或返回时稍作停留，让窗口交接完成。

### 关键口径与追问准备

- **时长占比**：正文与时长模块采用 67,957÷102,210=66.49%，范围为 5 分钟及以上、20 分钟以下；结论页仍有 63.7% 的旧文案。
- **前三热点**：按订单原数相加后计算为 59.54%；页面 59.6% 来自已舍入占比的相加，精确汇报采用前者。
- **OD 依据**：正文 85.11% 来自当前前端矩阵的对角线之和。旧 OD 脚本会独立重聚类，初始化设置也与热点主分析不同，不能直接混用区域编号与数字；当前矩阵尚缺统一导出链路，不将它宣称为已完整复现的离线产物。
- **为什么使用 GSAP**：多对象时序、可逆播放、路径变形、滚动联动和过程同步，都能由同一套时间线机制组织。
- **能否证明通勤或实时调度**：现有发现支持短途接驳解释，目的识别和运营决策还需外部数据验证。
